# Lab 01 트러블슈팅 — 콘솔에 입력하지 않은 모드 전환 메시지가 연달아 찍힘 (2026-09-21)

## 증상

M55 콘솔에 다음과 같이, 사용자가 그만큼 입력하지 않았는데도 모드 전환/상태조회 확인 메시지가 짧은 시간에 여러 번 연달아 출력되는 현상이 관찰되었습니다.

```
[IDLE] uptime=18062 ms -- sleeping 2000 ms (WFI expected)
>> ACTIVE mode: CPU stays ready, WFI never runs
>> IDLE mode: CPU sleeps via k_msleep()/WFI between bursts
>> IDLE mode: CPU sleeps via k_msleep()/WFI between bursts
>> IDLE mode: CPU sleeps via k_msleep()/WFI between bursts
>> Current mode: IDLE
>> Current mode: IDLE
>> ACTIVE mode: CPU stays ready, WFI never runs
```

## 진단

이 랩의 최초 버전(`uart_cmd_task`)은 `uart_poll_in()`으로 콘솔 UART에서 바이트를 하나 읽을 때마다, 그 바이트가 `'1'`/`'2'`/`'3'`이면 **곧바로** 모드를 전환하거나 상태를 출력하는 구조였습니다. 즉 어떤 경로로든 이 세 바이트 중 하나가 RX로 들어오기만 하면 실제 키 입력 여부와 무관하게 명령이 실행되었습니다.

관찰된 로그를 보면, 직전에 출력된 상태 메시지 `[IDLE] uptime=18062 ms -- sleeping 2000 ms (WFI expected)` 안에 `1`, `8`, `0`, `6`, `2`, `2`, `0`, `0`, `0`이라는 숫자가 그대로 들어 있습니다. 이 중 명령으로 해석될 수 있는 숫자(`1`, `2`)의 등장 순서가, 바로 다음에 찍힌 모드 전환 메시지들의 순서(ACTIVE → IDLE → IDLE)와 일치합니다. 이는 **M55가 콘솔로 내보낸 자기 자신의 출력(TX)이 어떤 경로로든 다시 자신의 수신(RX)으로 들어와, 로그 문자열 속 숫자가 명령으로 잘못 해석되고 있다**는 것을 강하게 시사합니다.

가능한 원인(우선순위 순, 아직 실기로 특정하지 못함 — TBD):

1. 콘솔에 사용 중인 USB-UART 컨버터/브릿지가 (일부 저가형 모듈에서 보이는) TX/RX 루프백 또는 half-duplex 에코 모드로 동작하고 있을 가능성.
2. J25 헤더를 외부 컨버터로 연결하는 배선에서 TX와 RX 핀이 실수로 서로 연결(쇼트)되었을 가능성.
3. 터미널 프로그램의 "Local echo"는 화면 표시용일 뿐 장치로 다시 전송되지 않는 것이 일반적이지만, 일부 터미널/설정 조합(예: half-duplex 강제 설정)에서는 실제로 장치 쪽으로 재전송될 수도 있어 완전히 배제하지는 않았습니다.

**근본 원인 확정을 위한 권장 확인 절차**: 아무 키도 누르지 않은 채로 1분 이상 콘솔을 관찰합니다. 이 시간 동안 `>> ACTIVE mode`/`>> IDLE mode`/`>> Current mode` 메시지가 저절로 계속 찍힌다면 위 진단이 맞다는 뜻이고, 반대로 아무 메시지도 추가로 찍히지 않는다면(순수하게 `[IDLE] uptime=...` 상태 로그만 2초 간격으로 이어진다면) 이전 관찰은 사용자가 실제로 여러 번 입력한 것일 뿐 이 문제가 아닙니다.

## 조치

근본 원인(하드웨어 loopback 여부)이 아직 확정되지 않았으므로, 우선 소프트웨어 쪽에서 이 문제를 원천적으로 걸러내는 방식으로 수정했습니다.

`uart_cmd_task`를 "숫자 한 바이트를 받으면 즉시 실행"하는 방식에서, **"숫자를 받으면 일단 보류하고, 그 직후 Enter(`\r` 또는 `\n`)가 들어와야 비로소 명령을 확정해서 실행"**하는 방식으로 변경했습니다.

```c
if (c == '\r' || c == '\n') {
        switch (pending_cmd) {
        case '1': /* ... ACTIVE로 전환 ... */ break;
        case '2': /* ... IDLE로 전환 ... */ break;
        case '3': /* ... 상태 출력 ... */ break;
        default: break;
        }
        pending_cmd = 0;
} else if (c == '1' || c == '2' || c == '3') {
        pending_cmd = c;
}
```

이 방식이 근본 원인과 무관하게 효과적인 이유는, 이 랩의 모든 로그 출력 문자열에서 숫자 바로 다음에 캐리지리턴/줄바꿈이 오는 경우가 없기 때문입니다(예: `"...18062 ms..."`의 `2` 다음에는 공백이 옵니다, 줄바꿈이 아닙니다). 반면 사람이 실제로 콘솔에 `1`을 입력하고 Enter를 누르면 정확히 "숫자 다음 곧바로 CR/LF"라는 패턴이 만들어집니다. 따라서 이 조치는 loopback으로 유입된 숫자를 실질적으로 걸러내면서, 정상적인 사용자 입력은 그대로 받아들입니다.

# 이슈 2 — ACTIVE 모드 진입 후 콘솔 명령이 전혀 먹지 않음 (2026-09-21)

## 증상

위 이슈 1의 조치(숫자+Enter 확정 방식) 적용 후 재검증한 결과, 이상 출력(저절로 찍히는 메시지)은 사라졌습니다. 그런데 부팅 직후 명령 몇 개는 정상 반영되어 ACTIVE 모드로 전환됐지만, 그 이후로는 콘솔에 `1`/`2`/`3` 중 무엇을 입력하고 Enter를 눌러도 아무 반응이 없고 `[ACTIVE] uptime=...` 로그만 2초 간격으로 계속 찍히는 상태로 고정되었습니다.

```
Boot mode: IDLE
[IDLE] uptime=39 ms -- sleeping 2000 ms (WFI expected)
>> ACTIVE mode: CPU stays ready, WFI never runs
>> IDLE mode: CPU sleeps via k_msleep()/WFI between bursts
>> ACTIVE mode: CPU stays ready, WFI never runs
[ACTIVE] uptime=2042 ms -- CPU never idles
[ACTIVE] uptime=4042 ms -- CPU never idles
... (계속 ACTIVE로 고정, 이후 어떤 명령도 반응 없음)
```

## 진단

원인은 스레드 우선순위 설계 실수였습니다.

- `uart_cmd_task`는 `K_THREAD_DEFINE`으로 우선순위 **5**로 생성했습니다.
- `main()`(ACTIVE/IDLE 워크로드가 도는 스레드)은 별도로 우선순위를 지정하지 않아 Zephyr 기본값(`CONFIG_MAIN_THREAD_PRIORITY`, 이 보드에서는 5보다 **숫자가 작은, 즉 더 높은 우선순위**)을 그대로 사용하고 있었습니다.
- ACTIVE 모드의 `main()` 루프는 `k_yield()`만 반복하며 절대 블로킹하지 않습니다. 그런데 `k_yield()`는 Zephyr 문서상 **"현재 스레드와 같은 우선순위의 다른 ready 스레드"**에게만 CPU를 양보하며, 낮은 우선순위 스레드에게는 양보하지 않습니다.
- 즉 `main()`이 `uart_cmd_task`보다 우선순위가 높은 상태에서 ACTIVE 모드에 들어가면, `main()`은 절대 블로킹하지 않고 `k_yield()`도 더 낮은 우선순위인 `uart_cmd_task`에게는 CPU를 넘기지 않으므로, **`uart_cmd_task`는 다시는 스케줄될 기회를 얻지 못합니다.** 그 결과 콘솔 UART를 폴링하는 코드 자체가 실행되지 않아, 이후 어떤 키를 입력해도 반영되지 않았던 것입니다.
- IDLE 모드에서는 문제가 없었던 이유: `main()`이 `k_msleep(2000)`으로 실제 블로킹하기 때문에, 그 사이 유일하게 ready 상태인 `uart_cmd_task`가 우선순위와 무관하게 정상적으로 스케줄됩니다. 그래서 "IDLE 상태에서 `1`을 입력해 ACTIVE로 전환하는 것"까지는 항상 성공했지만, 일단 ACTIVE에 들어간 뒤에는 영영 빠져나올 수 없었던 것입니다(부팅 직후 로그에서 ACTIVE→IDLE→ACTIVE로 두 번 더 전환된 것도, 아직 `main()`이 최초 IDLE 슬립 구간에 있었기 때문에 우연히 반영된 것입니다).

## 조치

`uart_cmd_task`의 우선순위를 `main()`보다 항상 높게(숫자를 더 작게) 재조정하고, `main()`은 시작 시 `k_thread_priority_set()`으로 자기 자신의 우선순위를 명시적으로 낮췄습니다.

```c
#define UART_CMD_THREAD_PRIORITY 1   /* higher priority (smaller number) */
#define WORKLOAD_THREAD_PRIORITY 10  /* lower priority */

K_THREAD_DEFINE(uart_cmd_tid, 1024, uart_cmd_task, NULL, NULL, NULL,
                 UART_CMD_THREAD_PRIORITY, 0, 0);

int main(void)
{
        k_thread_priority_set(k_current_get(), WORKLOAD_THREAD_PRIORITY);
        ...
}
```

이렇게 하면 `uart_cmd_task`가 자신의 `k_msleep(10)`에서 깨어날 때마다, 우선순위가 더 높으므로 낮은 우선순위인 `main()`의 `k_yield()` 루프를 **반드시 선점**해서 UART를 폴링할 기회를 얻습니다. `main()`이 ACTIVE 모드에서 절대 블로킹하지 않는다는 성질(=idle thread/WFI가 실행되지 않는다는 이 랩의 핵심 목적)은 그대로 유지되면서도, 명령 응답성은 보장됩니다.

## 교훈 (다른 랩에도 적용)

**"블로킹하지 않는 busy 루프"를 코드에 두는 경우, 그 스레드와 상호작용해야 하는 다른 모든 스레드(콘솔 명령 처리, 하트비트, IPC 콜백 워커 등)는 반드시 그보다 높은 우선순위를 가져야 합니다.** `k_yield()`는 "동일 우선순위에게만 CPU를 양보"하지 "더 낮은 우선순위에게도 양보"하지 않는다는 점을 반드시 기억해야 합니다. 이후 랩에서 blocking 없는 루프(예: 폴링 기반 워크로드)를 추가할 때는 이 우선순위 관계를 매번 명시적으로 점검할 것.

# 이슈 3 — 이슈 2 조치 이후에도 ACTIVE 모드에서 `1`만 반복 반영되고 `2`/`3`는 전혀 반응 없음 (콘솔 인터페이스 자체를 폐기하는 것으로 최종 마무리, 2026-09-21)

## 증상

이슈 2의 우선순위 조치를 반영한 뒤 재검증한 결과, ACTIVE 모드에 갇히는 문제는 사라졌지만(콘솔 명령 자체는 계속 처리되고 있음), 다음과 같이 **`>> ACTIVE mode: ...` 확인 메시지만 반복해서 찍히고, `2`나 `3`을 입력해도 `>> IDLE mode`나 `>> Current mode` 메시지가 전혀 나타나지 않는** 현상이 관찰되었습니다.

```
[ACTIVE] uptime=34907 ms -- CPU never idles
>> ACTIVE mode: CPU stays ready, WFI never runs
>> ACTIVE mode: CPU stays ready, WFI never runs
[ACTIVE] uptime=36907 ms -- CPU never idles
>> ACTIVE mode: CPU stays ready, WFI never runs
...
```

## 현재까지의 판단

이 로그에서 주목할 점은, 직전에 찍힌 어떤 상태 로그 문자열에도(`"34907"`, `"CPU never idles"` 등) 숫자 `1`이 들어 있지 않다는 것입니다. 즉 이슈 1에서 다뤘던 "로그 문자열 속 숫자가 loopback으로 재입력되는" 패턴과는 다릅니다. 또한 이슈 2에서 확인한 우선순위 문제라면 애초에 어떤 명령도(1/2/3 전부) 반영되지 않아야 하는데, `1`은 계속 반영되고 있으므로 우선순위 문제도 아닙니다.

현재로서는 다음 두 가지 가능성을 구분하지 못한 상태입니다.

1. 실제로 `2`/`3` 키를 누르셨는데도 그 바이트 자체가 M55의 UART RX에 전혀 도달하지 못하고 있을 가능성(배선/컨버터/터미널 프로그램의 키 매핑 문제 등)
2. `1`을 여러 번 테스트 삼아 누르신 것이고, `2`/`3`는 아직 시도하지 않으셨거나 다른 이유로 실제로는 전송되지 않았을 가능성

## 조치 — 임시 진단 코드 추가

원인을 추측으로 좁히는 대신, `uart_cmd_task`가 **실제로 수신하는 모든 raw 바이트를 그대로 로그로 출력**하도록 임시 진단 코드를 추가했습니다(`main.c`, "TEMPORARY DIAGNOSTIC" 주석 표시).

```c
printk("[uart_cmd_task] rx raw byte: 0x%02x ('%c')\n",
       c, (c >= 0x20 && c < 0x7f) ? (char)c : '.');
```

이 코드는 명령으로 인식되는지 여부와 무관하게, RX로 들어온 모든 바이트를 16진수와 출력 가능한 문자로 그대로 보여줍니다. 이를 통해 "2/3 키를 눌렀을 때 정말 아무 바이트도 안 들어오는지", 아니면 "바이트는 들어오는데 우리가 예상한 `0x32`(`'2'`)/`0x33`(`'3'`)가 아닌 다른 값인지"를 직접 구분할 수 있습니다.

**다음 확인 절차**: 재빌드/재플래시 후, `2`를 입력하고 Enter를 눌렀을 때 콘솔에 `[uart_cmd_task] rx raw byte: ...` 줄이 몇 개, 어떤 값으로 찍히는지 그대로 알려주시면 원인을 특정하겠습니다. 이 진단 코드는 원인이 밝혀지면 제거할 예정입니다.

## 후속 진단 — M4 교차간섭 가설, 실기로 반증됨 (2026-09-21)

임시 raw-byte 진단 코드(위 참고)를 반영해 재검증한 결과, 다음 값이 반복적으로 관찰되었습니다.

```
[uart_cmd_task] rx raw byte: 0x5b ('[')
[uart_cmd_task] rx raw byte: 0x30 ('0')
[uart_cmd_task] rx raw byte: 0x5d (']')
[uart_cmd_task] rx raw byte: 0x5b ('[')
...
"[0][INF][SYS ]:...Task vTaskDemo1" 형태의 문자열이 통째로 RX에 유입됨
```

이 문자열은 이 프로젝트의 어떤 Lab 01 코드에도 존재하지 않는 형식(FreeRTOS 스타일 로그 태그, `vTaskDemo1`이라는 태스크명)이었고, 마지막 `1` 바로 뒤에 개행이 오는 패턴이 이슈 3에서 관찰된 "`1`만 반복 반영"과 정확히 들어맞아, 최초에는 **"M4가 아직도 이 문자열을 찍는 이전/공장 출하 FreeRTOS 펌웨어로 남아있고, 그 출력이 배선을 통해 M55의 RX로 섞여 들어온다"는 가설**을 세우고, M4 콘솔을 직접 확인하고 M4의 UART 어댑터를 뽑아 M55 단독으로 재현되는지 확인해달라고 요청했습니다.

**결과: 이 가설은 실기로 반증되었습니다.**

- M4 콘솔은 완전히 정상이었습니다 — `=== Lab 01 (M4): Always-On heartbeat ===` 배너와 `[M4 heartbeat] tick=N, uptime=... ms`만 깨끗하게 출력되고, 의심되던 FreeRTOS 로그 형식은 전혀 없었습니다.
- M55를 M4와 완전히 분리해 단독으로 연결한 상태에서도 동일한 가비지 문자열이 그대로 재현되었습니다.

즉 M4의 배선/펌웨어와는 무관한 문제입니다. 사용자가 과거에 겪었던 **"M55 콘솔 프로그램(PC 쪽 시리얼 모니터 툴) 자체의 버그"**를 의심할 만한 근거가 있어, 이번에는 이 콘솔 프로그램 자체를 디버깅하는 대신(이 커리큘럼의 범위를 벗어남), **UART 콘솔 명령 인터페이스를 아예 폐기**하는 방향으로 최종 결론을 내렸습니다.

## 최종 조치 — 콘솔 명령을 온보드 버튼(SW8)으로 교체

`uart_cmd_task`, 임시 raw-byte 진단 코드, Enter 확정 로직을 포함한 UART 명령 처리 코드를 전부 제거했습니다. 대신 이 프로젝트의 M4↔M55 IPC 커리큘럼에서 이미 검증된 온보드 물리 버튼 **SW8("USER_BUTTON")**을 M55에서 직접 읽어, 누를 때마다 ACTIVE/IDLE을 토글하는 방식으로 재설계했습니다(Zephyr `zephyr/input/input.h` 입력 서브시스템, `INPUT_CALLBACK_DEFINE()`).

이 교체로 다음이 함께 해결됩니다.

- 모드 전환이 더 이상 콘솔 UART의 RX 경로를 전혀 거치지 않으므로, 원인이 무엇이었든 그 콘솔 프로그램 버그의 영향을 받지 않습니다.
- 이슈 2에서 다룬 스레드 우선순위 이슈(`uart_cmd_task` vs `main()`)도 함께 해소됩니다 — 입력 서브시스템 콜백은 시스템 워크큐 스레드(cooperative 우선순위)에서 실행되므로, `main()`의 우선순위를 낮추는 별도 조치 없이도 ACTIVE 모드의 busy loop을 항상 선점할 수 있습니다.

다만 SW8은 직접 SoC GPIO가 아니라 I2C1 버스에 물린 PCA6416A GPIO 익스팬더(`gpio_exp0`) 뒤에 있는 버튼입니다. IPC 커리큘럼에서 M4 쪽 `gpio_exp0`는 `int-gpios`가 없어 인터럽트를 지원하지 않고(`-ENOTSUP`, `&buttons { polling-mode; };`로 우회) 했던 것과 달리, **M55 쪽 `gpio_exp0`는 `int-gpios`가 정의되어 있음이 그 커리큘럼에서 이미 확인**되어 있어, 이번에는 M55에서 인터럽트 기반으로 정상 동작할 것으로 예상합니다 — 다만 이 조합(M55 + gpio_exp0 인터럽트)은 이 프로젝트에서 처음 실기 검증하는 것이므로 **TBD**입니다. 만약 부팅 로그에 `gpio_keys: interrupt configuration failed: -134`가 나타나면, IPC 커리큘럼과 동일하게 M55 오버레이의 `&buttons` 노드(자식 `&user_button`이 아님)에 `polling-mode;`를 추가하면 됩니다:

```dts
&buttons {
	polling-mode;
};
```

또한 M55가 I2C1을 마스터해야 하므로, 이 랩의 오버레이 구성이 이전 버전과 반대로 바뀌었습니다 — 상세는 갱신된 `01_baseline_active_idle_kr.md`의 "Devicetree 오버레이" 절을 참고하세요.

**이 이슈는 근본 원인(콘솔 프로그램 버그 자체)을 확정하지 못한 채로 종결합니다** — 이 커리큘럼은 전력 관리 학습이 목적이므로, PC 쪽 도구 자체의 버그를 추적하는 대신 그 도구에 의존하지 않는 설계로 우회했습니다. 콘솔 프로그램의 정확한 결함은 TBD로 남겨둡니다.

# 이슈 4 — v2(SW8 버튼) 재설계 후, 부팅 후 첫 눌림(IDLE→ACTIVE)만 반영되고 그 다음부터는 반응 없음 (2026-09-21, polling-mode로 해결)

## 증상

콘솔 명령을 SW8 버튼으로 교체한 v2를 실기에 플래시한 뒤:

```
Boot mode: IDLE
[IDLE] uptime=50 ms -- sleeping 2000 ms (WFI expected)
...
>> [SW8] ACTIVE mode: CPU stays ready, WFI never runs
[ACTIVE] uptime=14068 ms -- CPU never idles
[ACTIVE] uptime=16068 ms -- CPU never idles
... (이후 SW8을 다시 눌러도 `>> [SW8] IDLE mode` 메시지가 전혀 나타나지 않고 [ACTIVE] 로그만 계속됨)
```

부팅 후 첫 번째 버튼 입력(IDLE→ACTIVE)은 정상 반영되었지만, 그 다음 버튼 입력(ACTIVE→IDLE로 되돌리려는 시도)은 완전히 무반응이었습니다.

## 진단

`main.c`의 모드 토글 로직 자체는 IDLE→ACTIVE와 ACTIVE→IDLE이 완전히 대칭적인 코드(`if (mode == MODE_ACTIVE) { ... } else { ... }`)이므로, 애플리케이션 로직에는 방향에 따른 비대칭이 없습니다. 그런데도 한쪽 방향만 실패한다는 것은, 애플리케이션에 도달하기 전 단계 — 즉 `gpio_exp0`(PCA6416A) 인터럽트 자체가 **최초 1회만 발생하고 그 이후로는 다시 걸리지 않는다**는 뜻입니다.

이는 I2C GPIO 익스팬더 뒤에 물린 버튼에서 흔히 나타나는 유형의 문제입니다 — 익스팬더의 `INT#` 핀은 입력 포트 레지스터를 I2C로 읽어야 비로소 해제(재무장)되는데, 이 재무장 처리(디바운스 후 다음 엣지에 대비해 인터럽트를 다시 구성하는 과정 등)가 정확히 맞물리지 않으면 두 번째 이후의 전환은 인터럽트 자체가 걸리지 않게 됩니다. 이 프로젝트의 M4↔M55 IPC 커리큘럼에서 M4가 `gpio_exp0`의 `int-gpios` 부재로 인터럽트를 아예 지원받지 못해 `&buttons { polling-mode; };`로 우회했던 것과 **증상은 다르지만(M55는 int-gpios가 있어 최소 1회는 동작), 결과적으로 같은 부류의 "I2C 익스팬더+인터럽트 기반 gpio-keys" 불안정성**입니다.

## 조치

M55 오버레이에도 동일한 `polling-mode`를 적용했습니다(`lab/boards/sr100_rdk_sr100_m55.overlay`):

```dts
&buttons {
	polling-mode;
};
```

인터럽트 기반 대신 주기적으로 GPIO 익스팬더 레지스터를 폴링하는 방식이라, 매 전환마다 재무장 문제가 발생할 여지가 없습니다. `debounce-interval-ms` 기본값(30ms)은 이 랩에 충분합니다(IPC 커리큘럼에서 이미 검증됨).

**다음 확인 절차**: 재빌드(`-p always` 권장 — devicetree 변경이므로 빌드 캐시 이슈 재발 가능, 11.1절 참고)/재플래시 후, SW8을 여러 번 연속으로 눌러 ACTIVE↔IDLE이 매번 정상적으로 토글되는지 확인해 주세요.

# 이슈 5 — polling-mode 적용 후에도 동일 증상 재발: 최초 1회(IDLE→ACTIVE)만 반영, 이후 무반응 (스레드 우선순위 가설 — 실기로 반증됨, 6번 참고, 2026-09-21)

## 증상

이슈 4의 조치(`&buttons { polling-mode; };`)를 적용하고 재검증했으나, 동일한 증상이 그대로 재현되었습니다 — 부팅 후 첫 번째 버튼 입력(IDLE→ACTIVE)만 반영되고, 그 이후 버튼을 다시 눌러도(ACTIVE→IDLE로 되돌리려는 시도) 전혀 반응이 없습니다.

## 현재까지의 판단

인터럽트 모드와 polling-mode는 하드웨어/재무장 메커니즘이 서로 다른데도 정확히 같은 증상이 재현된다는 것은, 원인이 그 아래 계층(인터럽트 재무장, 폴링 주기 등)이 아니라 **두 모드가 공통으로 거치는 더 상위의 로직**에 있다는 뜻입니다. 가장 유력한 가설은 다음과 같습니다.

**뗌(release, value=0) 이벤트가 드라이버 레벨에서 누락되고 있을 가능성.** `input_gpio_keys` 드라이버는 내부적으로 "이전에 안정화된 상태"와 "새로 읽은 상태"를 비교해 값이 달라졌을 때만 이벤트를 report합니다. 만약 버튼을 뗀 뒤에도 드라이버가 여전히 "눌림" 상태로 읽고 있다면(예: `gpio_exp0`에서 두 번째 이후 I2C 읽기가 실패해 이전 값을 그대로 쓰는 경우, 또는 극성/디바운스 설정 문제), 그 다음 실제 눌림은 드라이버 입장에서 "이미 눌린 상태 → 눌림"이라 상태 변화가 없어 이벤트 자체가 발생하지 않습니다. 이는 인터럽트 모드든 polling-mode든 동일하게 나타날 수 있는 상위 로직이라, 관찰된 증상과 정확히 들어맞습니다.

## 조치 — 임시 진단 코드 추가

원인을 추측으로 좁히는 대신, `button_input_cb`가 필터링 없이 **모든 raw 입력 이벤트**(type/code/value)를 그대로 로그로 출력하도록 임시 진단 코드를 추가했습니다(`main.c`, "TEMPORARY DIAGNOSTIC" 주석 표시).

```c
printk("[button_input_cb] type=0x%02x code=0x%02x value=%d\n",
       evt->type, evt->code, evt->value);
```

**다음 확인 절차**: 재빌드/재플래시 후, SW8을 눌렀다 뗐다를 여러 번(최소 3~4회) 반복하면서 콘솔에 `[button_input_cb] ...` 줄이 매번 찍히는지, 찍힌다면 `value`가 press/release마다 1과 0을 정상적으로 번갈아 나타내는지 그대로 알려주시면 원인을 특정하겠습니다.

- 만약 두 번째 눌림부터 `[button_input_cb]` 로그 자체가 전혀 안 찍힌다면 → `gpio_exp0`/I2C1 버스 레벨에서 값 변화 자체를 못 읽어오는 문제(I2C 트랜잭션 실패 등)로 좁혀집니다.
- 만약 로그는 찍히는데 `value`가 이상하게 나온다면(예: release가 안 오거나, 항상 같은 값이거나) → 디바운스/극성 설정 문제로 좁혀집니다.

이 진단 코드는 원인이 밝혀지면 제거할 예정입니다.

## 후속 진단 — raw 이벤트 로그로 원인 확정 (2026-09-21)

진단 코드 반영 후 재검증 결과, 결정적인 로그를 확보했습니다.

```
[IDLE] uptime=8058 ms -- sleeping 2000 ms (WFI expected)
[button_input_cb] type=0x01 code=0x0b value=1
>> [SW8] ACTIVE mode: CPU stays ready, WFI never runs
[button_input_cb] type=0x01 code=0x0b value=0
[ACTIVE] uptime=10060 ms -- CPU never idles
[ACTIVE] uptime=12060 ms -- CPU never idles
... (이후 SW8을 아무리 여러 번 눌러도 [button_input_cb] 로그 자체가 단 한 줄도 더 찍히지 않음)
```

**핵심 관찰**: 최초의 press(`value=1`)와 release(`value=0`) 두 이벤트가 **모두** 정상적으로 잡혔습니다 — 즉 이슈 5 초반에 세웠던 "release 이벤트 누락" 가설은 틀렸습니다. 문제는 정확히 **ACTIVE 모드로 전환된 그 순간부터** 콜백 자체가(원본 raw 이벤트조차) 완전히 멈춘다는 점입니다.

## 원인 확정

이 랩의 `button_input_cb`는 입력 서브시스템의 **워크큐 스레드**(ISR이 아님)에서 호출됩니다. 저는 처음에 "시스템 워크큐는 cooperative(음수) 우선순위라 항상 다른 스레드를 선점한다"고 가정하고 코드/문서에 그렇게 적었는데, **이 가정은 검증 없이 세운 것이었고 이번 SDK에서는 틀렸던 것으로 보입니다.**

`main()`은 별도로 우선순위를 낮추지 않아 Zephyr 기본 우선순위(preemptible, 이 SDK에서 워크큐보다 같거나 높은 우선순위)로 돌고 있었습니다. ACTIVE 모드의 `main()` 루프는 `k_yield()`만 반복하며 절대 블로킹하지 않는데, `k_yield()`는 **같은 우선순위**의 다른 ready 스레드에게만 CPU를 양보하지, 자신보다 우선순위가 낮은(혹은 같지 않은) 스레드에게는 양보하지 않습니다. 즉 워크큐 스레드가 `main()`보다 낮은(혹은 같지 않은) 우선순위였다면, ACTIVE 모드에 들어간 순간부터 `main()`의 무한 `k_yield()` 루프가 워크큐 스레드를 영원히 굶겨서, SW8의 GPIO 값 변화 자체를 폴링/처리할 기회를 잃게 됩니다. IDLE 모드에서는 `main()`이 `k_msleep()`으로 실제 블로킹하므로 워크큐가 정상적으로 스케줄되고, 그래서 부팅 후 최초의 IDLE→ACTIVE 전환(press+release 둘 다)까지는 항상 정상 동작했던 것입니다.

이는 이 랩의 v1(콘솔 명령 버전)에서 `uart_cmd_task` vs `main()` 사이에 있었던 것과 **완전히 동일한 유형의 우선순위 버그**입니다(이슈 2 참고) — 이번엔 상대가 직접 만든 스레드가 아니라 Zephyr 입력 서브시스템의 워크큐였을 뿐입니다.

## 조치

`main()`이 시작 시 `k_thread_priority_set()`으로 자기 자신의 우선순위를 명시적으로 낮추도록(숫자를 크게, 즉 우선순위를 낮게) 되돌렸습니다 — v1에서 썼던 것과 같은 조치입니다.

```c
#define WORKLOAD_THREAD_PRIORITY 10

int main(void)
{
        k_thread_priority_set(k_current_get(), WORKLOAD_THREAD_PRIORITY);
        ...
}
```

이 SDK의 `CONFIG_SYSTEM_WORKQUEUE_PRIORITY` 정확한 기본값은 확인하지 않았습니다(TBD) — 대신 `main()`을 확실히 낮은(숫자가 큰) 우선순위로 내려서, 워크큐 스레드의 우선순위가 무엇이든 항상 `main()`의 ACTIVE busy loop을 이길 수 있도록 했습니다.

**다음 확인 절차**: 재빌드/재플래시 후, ACTIVE 모드에 들어간 뒤에도 SW8을 누를 때마다 `[button_input_cb]` 로그가 계속 찍히고 ACTIVE↔IDLE이 매번 정상 토글되는지 확인해 주세요. 확인되면 진단용 raw 이벤트 로그(`printk("[button_input_cb] ...")`)는 다음 리비전에서 제거하겠습니다.

## 교훈 (다른 랩에도 적용)

**"블로킹하지 않는 busy 루프"를 코드에 두는 경우, 그 스레드와 상호작용해야 하는 다른 모든 스레드(직접 만든 스레드뿐 아니라 Zephyr가 내부적으로 쓰는 워크큐 스레드도 포함)는 반드시 그 busy loop보다 높은 우선순위를 갖는지 명시적으로 확인/보장해야 합니다.** "시스템 워크큐는 기본적으로 cooperative 우선순위일 것"이라는 가정은 이 SDK에서 확인 없이 신뢰해서는 안 됩니다 — 이슈 2에서 얻은 교훈이 워크큐에도 동일하게 적용되는 사례입니다.

# 이슈 6 — 이슈 5의 우선순위 가설, 실기로 반증됨: gpio-keys 서브시스템 자체를 우회하는 것으로 최종 해결 (2026-09-21)

## 증상

이슈 5에서 세운 "워크큐 스레드가 `main()`의 ACTIVE busy loop에 굶주린다"는 가설에 따라 `main()`의 우선순위를 명시적으로 낮췄으나(`k_thread_priority_set()`), 재검증 결과 **완전히 동일한 증상이 그대로 재현**되었습니다 — 부팅 후 최초 1회(press+release 모두 정상 로그)만 반영되고, 그 이후 SW8을 아무리 눌러도 `[button_input_cb]` 로그 자체가 단 한 줄도 더 찍히지 않았습니다.

```
[IDLE] uptime=4053 ms -- sleeping 2000 ms (WFI expected)
[button_input_cb] type=0x01 code=0x0b value=1
>> [SW8] ACTIVE mode: CPU stays ready, WFI never runs
[button_input_cb] type=0x01 code=0x0b value=0
[ACTIVE] uptime=6055 ms -- CPU never idles
... (이후 무한 반복, SW8 눌러도 무반응)
```

## 진단 — 우선순위 가설 반증, 사용자 지적으로 재검토

사용자가 다음 세 가지를 지적했습니다: (1) 정말 우선순위 문제라면 Zephyr 커뮤니티에 이미 잘 알려졌을 흔한 패턴일 텐데 이 정도로 완전히 막히는 게 이상하다, (2) 진짜 우선순위 문제라면 `k_yield()` 대신 `k_msleep(1)`만 넣어도 (스레드가 ready 큐에서 완전히 빠지므로) 우회될 것이다, (3) 애초에 key event/interrupt 처리는 스레드 우선순위보다 위에 있는 것 아니냐.

이 지적들을 반영해 재검토한 결과:

- (1), (2)는 이론적으로 타당하지만, 실기로 `main()` 우선순위를 명시적으로 낮췄는데도 증상이 그대로 재현됐다는 사실 자체가 **우선순위 가설을 직접 반증**합니다. 워크큐 스레드가 진짜로 `main()`보다 우선순위가 낮아서 굶주리는 것이었다면, `main()`을 더 낮은 우선순위로 내렸을 때 반드시 해소됐어야 합니다.
- (3)이 결정적인 지적이었습니다 — **진짜 하드웨어 인터럽트(ISR)는 스레드 우선순위 체계 바깥에 있어 항상 이기는 게 맞지만, `polling-mode`는 정의상 인터럽트를 아예 안 쓰고 워크큐 스레드가 주기적으로 폴링하는 방식**입니다. 게다가 인터럽트 모드였던 이슈 4조차, ISR 안에서 직접 I2C 트랜잭션(블로킹)을 할 수 없어서 실제 레지스터 읽기는 결국 ISR이 깨우는 워크큐 스레드에서 처리되는 구조였을 가능성이 높습니다. 즉 인터럽트 모드든 polling-mode든 "SW8 눌림을 실제로 처리하는 코드"는 결국 둘 다 스레드 컨텍스트(워크큐)에서 돌고 있었다는 뜻이지만, **그 스레드가 우선순위 때문에 굶주린 게 아니라는 것이 이번 재검증으로 확인**되었습니다.

**결론**: 원인은 스레드 우선순위가 아니라, **이 SDK의 `gpio-keys`/`input_gpio_keys` 드라이버 자체의 폴링/인터럽트 상태머신에 있는 버그**로 좁혀집니다(정확한 내부 메커니즘은 미규명 — 소스 미확보 상태에서는 더 이상 추측하지 않습니다).

## 조치 — Zephyr gpio-keys/input 서브시스템을 우회, 애플리케이션에서 직접 GPIO 폴링

더 이상 이 드라이버를 추측으로 디버깅하지 않고, 이 랩의 v1이 UART 명령 처리에 썼던 것과 동일한 철학(자체 sample-and-debounce)으로 **SW8을 plain GPIO API(`gpio_pin_get_dt()`)로 직접 읽는 방식**으로 전환했습니다.

- `main.c`: `zephyr/input/input.h`/`INPUT_CALLBACK_DEFINE()`를 전부 제거. 대신 `user_button` devicetree 노드의 기존 `gpios` 프로퍼티를 `GPIO_DT_SPEC_GET(DT_NODELABEL(user_button), gpios)`로 직접 가져와, 전용 스레드(`button_poll_task`, 우선순위 1)가 20ms마다 폴링하며 3회 연속 동일 값이 나와야 상태 변화로 확정하는 간단한 디바운스를 자체 구현했습니다. `main()`은 v1과 동일하게 자기 우선순위를 10으로 낮춰, `button_poll_task`가 항상 우선권을 갖도록 보장합니다(이 우선순위 배치는 v1에서 이미 실기로 검증된 패턴).
- `boards/sr100_rdk_sr100_m55.overlay`: `&buttons { polling-mode; };` 제거(더 이상 그 드라이버를 쓰지 않으므로 불필요). `&i2c1`/`&gpio_exp0`는 그대로 활성화 유지(직접 GPIO 접근에도 필요).
- `prj.conf`: `CONFIG_INPUT`/`CONFIG_INPUT_GPIO_KEYS` 제거.
- 진단용 printk(raw 읽기 에러, 매 상태 변화)를 유지해서, 이번에도 원인이 I2C/하드웨어 레벨인지 확인 가능하도록 했습니다.

**이 조치는 진단을 겸합니다**: 만약 이 방식도 최초 1회 이후 멈춘다면 원인은 gpio-keys 드라이버가 아니라 I2C1/gpio_exp0 하드�디어 레벨(버스 lock-up 등)이라는 뜻이고, 계속 정상 동작한다면 gpio-keys 드라이버 자체의 버그였다는 것이 확정됩니다.

**다음 확인 절차**: 재빌드(`-p always` 권장 — prj.conf/오버레이 변경)/재플래시 후, ACTIVE 모드에서도 SW8을 여러 번 반복해서 눌러 매번 `[button_poll_task] stable state -> ...` 로그가 찍히고 ACTIVE↔IDLE이 정상 토글되는지 확인해 주세요.

## 정정 — 이슈 4/5의 "인터럽트 재무장 실패"/"워크큐 우선순위" 진단은 근거 부족으로 철회

이슈 4에서 세운 "M55의 `gpio_exp0` 인터럽트가 재무장되지 않는다"는 진단과, 이슈 5에서 세운 "워크큐 스레드가 우선순위 때문에 굶주린다"는 진단은 모두 **증상(최초 1회만 동작)을 설명하기 위해 세운 가설이었을 뿐, 실기로 직접 검증되지 않았고 이번 우선순위 조치의 실기 반증으로 근거가 사라졌습니다.** 진짜 원인은 이 SDK의 gpio-keys 드라이버 내부 버그(정확한 메커니즘 미규명)로 보는 것이 현재로서는 가장 근거 있는 설명이며, 이번 조치(드라이버 우회)가 이를 최종 확인해 줄 것입니다.

# 이슈 7 — v3의 `button_poll_task`가 IDLE 측정 자체를 오염시킴: 스레드 제거, main() 통합 폴링으로 재설계 (2026-09-21)

## 문제 — 실기 테스트 전, 설계 리뷰 단계에서 발견

v3를 실기에 올리기 전에, 사용자가 v3 설계를 검토하다가 결정적인 결함을 지적했습니다: **"Zephyr의 gpio-keys/input 서브시스템을 걷어내고 직접 GPIO를 폴링하는 방향은 동의하지만, `button_poll_task`가 `k_msleep(20)`으로 20ms마다 무한 반복하는 것은 IDLE 모드에서도 똑같이 동작한다 -- 그러면 IDLE 상태에서도 CPU가 20ms마다 계속 깨어나게 되는 것 아니냐?"**

정확한 지적입니다. v3의 `button_poll_task`는 `g_mode` 값과 무관하게 항상 20ms 주기로 깨어나 실행됩니다. 즉 IDLE 모드가 "CPU가 WFI로 잠든다"를 보여주려는 의도였음에도, 실제로는 이 폴링 스레드가 20ms마다 CPU를 깨우기 때문에 **멀티미터로는 깨끗한 WFI-sleep 베이스라인 전류를 절대로 볼 수 없고, 매번 20ms 주기의 wake 스파이크가 겹친 전류만 보이게 됩니다.** 이는 이 랩의 존재 목적(ACTIVE vs IDLE 전류 베이스라인 측정) 자체를 무력화하는 설계 결함이며, gpio-keys 드라이버 버그 여부와는 완전히 별개의 문제입니다.

## 조치 — 전용 스레드 제거, `main()` 루프에 모드별로 다르게 통합

v4에서는 `button_poll_task` 스레드와 `K_THREAD_DEFINE()`을 완전히 제거하고, 버튼 폴링을 `main()`의 기존 루프 안으로 흡수했습니다. 모드마다 폴링 방식을 다르게 가져가서 **어느 모드의 전류 프로파일도 건드리지 않도록** 했습니다.

- **IDLE**: `main()`이 상태 로그를 위해 이미 하고 있던 `k_msleep(IDLE_SLEEP_MS)`(2초) 직후, 그 김에 버튼을 딱 한 번만 읽습니다. CPU가 어차피 그 시점에 깨어날 예정이었으므로 **추가 wake 이벤트가 전혀 생기지 않습니다.** 디바운스도 별도로 두지 않았는데, 2초라는 샘플링 간격 자체가 기계식 버튼의 채터링(수 ms 수준)보다 훨씬 길어서 자연스럽게 걸러지기 때문입니다.
- **ACTIVE**: v3와 동일하게 20ms 주기 + 3회 연속 동일값 디바운스를 그대로 쓰되, 그 주기를 `k_msleep()`이 아니라 기존 `ACTIVE_LOG_PERIOD_MS` 로그 출력과 똑같은 방식(`k_uptime_get_32()` 값을 논블로킹으로 비교)으로 구현했습니다. ACTIVE 모드의 존재 이유가 "CPU가 항상 ready 상태라 WFI가 절대 안 돈다"이므로, 이 분기 안에 `k_msleep()`을 하나라도 넣으면 그 자체로 ACTIVE가 만들려던 유휴 구간이 다시 생겨버립니다.
- 스레드가 하나(main 하나)만 남았으므로, v3에서 필요했던 `button_poll_task` vs `main()` 우선순위 조정도 함께 사라졌습니다 -- 더 이상 굶길 대상이 없습니다.

## 참고

이 변경은 gpio-keys 드라이버 버그 규명(이슈 6)과는 독립적인 이슈입니다. v4도 여전히 `gpio_pin_get_dt()`로 raw GPIO를 읽는 v3의 방식을 그대로 쓰므로, 이슈 6에서 세운 진단 계획(최초 1회 이후 멈추면 I2C/하드웨어 레벨, 계속 동작하면 gpio-keys 드라이버가 원인)은 v4에도 동일하게 적용됩니다. 이 랩의 실기 테스트는 아직 v3/v4 어느 버전으로도 완료되지 않았습니다.

# 실기 확인 결과 (2026-09-21) — v4 최종 동작 확인, 알려진 지연 특성 기록

## 결과: gpio-keys 우회(raw GPIO 폴링) 방식이 실기에서 반복 정상 동작함을 확인

v4를 실기에 올려 SW8을 여러 차례 반복해서 눌러본 결과, **최초 1회 이후 멈추는 증상 없이 ACTIVE↔IDLE 토글이 계속 정상 동작**했습니다. 이로써 이슈 4~7에 걸친 진단이 최종 확정됩니다: 원인은 I2C1/`gpio_exp0` 하드웨어 레벨이 아니라 **이 SDK의 Zephyr `gpio-keys`/`input` 서브시스템 드라이버 내부 상태머신의 버그**였고(정확한 내부 메커니즘은 여전히 미규명이나, 더 이상 이 랩의 범위에서 추적하지 않습니다), plain GPIO 직접 폴링으로 완전히 우회되었습니다.

## 알려진 특성(버그 아님): IDLE → ACTIVE 전환에 최대 약 2초 지연

v4는 IDLE 모드에서 버튼을 `k_msleep(IDLE_SLEEP_MS)`(2초) 직후 한 번만 샘플링하므로, SW8을 누른 시점에 따라 ACTIVE 모드로 실제 전환되기까지 **최대 약 2초, 평균 약 1초의 지연**이 있습니다(ACTIVE → IDLE 방향은 20ms 폴링이라 사실상 즉시 반응). 이는 이슈 7에서 의도적으로 선택한 트레이드오프의 직접적인 결과이며, 다음과 같이 최종 결론짓습니다.

- **의도적으로 남겨둔 특성입니다.** 더 빠르게 반응하려면 IDLE 중에도 더 자주 깨어나야 하는데, 그러면 이슈 7에서 고친 "IDLE 전류 측정 오염" 문제가 다시 발생합니다. 즉 **"낮은 전력"과 "빠른 반응성"은 이 아키텍처에서 서로 트레이드오프 관계**이고, 이 랩은 전류 측정이 목적이므로 반응성보다 측정 순수성을 택했습니다.
- 더 빠른 반응이 필요하다면 `gpio_pin_interrupt_configure_dt()` + `gpio_add_callback()`으로 gpio-keys/input 서브시스템을 거치지 않는 raw 인터럽트를 직접 구성하는 방법이 이론적으로 있습니다(즉시 wake, 폴링 오버헤드 없음). 다만 이슈 4에서 실패했던 것도 인터럽트 기반 경로였다는 점에서 동일 계열의 미규명 드라이버 버그를 다시 만날 위험이 있고, 이 랩의 학습 목표(ACTIVE/IDLE 전류 베이스라인 측정) 범위를 벗어나는 추가 디버깅이 필요합니다. **이번 커리큘럼에서는 시도하지 않고, 향후 실험 아이디어로만 남겨둡니다.**

## 결론

Lab 01은 이 결과로 최종 확정합니다. IDLE↔ACTIVE 토글, ACTIVE/IDLE 각각의 전류 측정, 그리고 위에서 기록한 IDLE→ACTIVE 지연 특성까지 모두 실기로 확인되었습니다.

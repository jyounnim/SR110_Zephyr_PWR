# Lab 05 — 종합: 리셋 원인 기반 설계 가이드

**상태: 실기 확인 완료, 최종 마무리(2026-09-22).**

이 커리큘럼의 마지막 랩입니다. 새로운 하드웨어 현상을 탐색하는 랩이 아니라, Lab 00~04에서 확인한 것들을 하나의 "실제 제품이라면 이렇게 짤 것이다"라는 대표 코드와 설계 가이드로 종합합니다.

## 학습 목표

- 부팅 초입에서 `hwinfo_get_reset_cause()`를 항상 체크해, 이번 부팅이 어떤 원인이었는지에 따라 분기하는 **표준 부트 처리 패턴**을 실습합니다.
- Lab 01~04를 종합해, 이 SDK/보드에서 확인된 각 "깨어남" 방식의 트리거·재개 방식(컨텍스트 보존 여부)·상대적 반응 속도·실기 검증 상태를 하나의 비교표로 정리합니다.
- 이 SDK에는 **"컨텍스트를 보존한 채 깊이 자는 중간 단계"(Zephyr `PM_STATE_SUSPEND_TO_RAM`류)가 없고, WFI(얕음, 즉시 재개) 아니면 리셋(깊음, 완전 재부팅) 두 단계만 있다**는 결론을 명시적으로 정리합니다.
- 이 SoC의 원래 설계 의도 — **M4가 Always-On으로 감시하다가, 의미 있는 이벤트가 있을 때만 M55를 깨운다** — 를 재현하는 대표 코드로 커리큘럼을 마무리합니다.

## 이전 랩과의 연결

Lab 00에서 세웠던 세 가지 확인 질문(1-3절)에 대한 최종 답변을 코드로 매듭짓는 랩입니다.

- Lab 01은 이 SDK에 `CONFIG_PM`이 없다는 것(Lab 00)을 실기로 받아들이고, 순수 idle thread 자동 WFI만으로 baseline을 잡았습니다 — **"얕은 깨어남"**.
- Lab 02는 M55 전용 watchdog을 실기로 확인했지만, `WDT_FLAG_RESET_SOC`가 자체 완결되는 안전장치型 리셋으로 확인되지 않는다는, 예상 밖의 결과로 마무리됐습니다 — **"깊은 깨어남(리셋)"이지만 불완전함**.
- Lab 03은 별도 IPC 커리큘럼의 mbox 패턴을 재사용해, **리셋 없이, 살아있는 채로** M4가 M55를 깨우는 것을 정확히 의도대로 확인했습니다 — 이 커리큘럼이 원래 찾고 있던 "M4가 M55를 깨우는 공식 경로"에 대한 사실상의 답입니다.
- Lab 04는 `SW7`/`PMU_EN` 경로를 탐색했지만, 이 SDK에 저전력 모드 진입 API 자체가 없어 "의미 있는 wake-up" 검증이 범위 밖이라는 것을 확인했습니다.

이 랩은 Lab 02/04에서 확인된 두 가지 한계(리셋이 자체 완결되지 않음 / 저전력 모드 진입 경로 없음)를 **회피하지 않고 코드 주석에 명시한 채로**, Lab 01의 baseline 개념과 Lab 03의 확실히 동작하는 mbox 패턴, Lab 02의 부트 원인 진단 패턴을 하나로 합칩니다.

## 하드웨어 구성

Lab 03과 동일합니다 — M4가 I2C1을 마스터해 온보드 가속도계(`mc3479`)를 읽고, M55는 mbox rx만 엽니다. M55 콘솔과 M4 콘솔을 모두 열어둡니다.

## Devicetree 오버레이

Lab 03의 오버레이를 **그대로 재사용**합니다 (M55: `i2c1`/`gpio_exp0`/`ov02c10` 비활성화, M4: `mc3479` 활성화, 양쪽 `ipc0` shared-memory-size 0x400 일치).

## 코드 구성

### M55 (`lab/src/main.c`)

두 부분으로 구성됩니다.

1. **`handle_boot_reset_cause()`** — Lab 02/04에서 쓰던 디코딩 패턴에, 카테고리별로 "실제 제품이라면 이 상황에서 뭘 해야 하는가"에 대한 한 줄 코멘트를 붙였습니다.
   - `RESET_PIN`/`RESET_SOFTWARE`: 정상 콜드 스타트.
   - `RESET_WATCHDOG`: Lab 02에서 이 SDK/보드가 이 리셋을 스스로 완결하지 못한다는 것을 확인했으므로, 이 원인이 실제로 반복해서 찍힌다면 일상적인 부팅이 아니라 **진짜 장애 신호로 취급하고 로깅/카운팅해야 한다**는 코멘트.
   - `RESET_POR`: 이 보드에서는 물리 System Reset 버튼(Lab 02)도, PMU_EN 기반 wake(Lab 04, 미확정)도 이 비트로 겹쳐 보고될 수 있어 이 비트 하나만으로는 구분할 수 없다는 코멘트.
   - `RESET_LOW_POWER_WAKE`: 이 커리큘럼에서는 소프트웨어로 재현하지 못했지만(Lab 04), 만약 실제 RTC/PIR 하드웨어에서 이 값이 찍힌다면 그건 이 코드가 아니라 진짜 AON 하드웨어에서 온 것이라는 코멘트.
2. **mbox 이벤트 루프** — Lab 03의 M55 코드를 **그대로** 재사용합니다. `handle_boot_reset_cause()` 호출 뒤, mbox rx 채널을 열고 `k_msgq_get(..., K_FOREVER)`로 대기 — M4 이벤트가 올 때마다 로그를 남기고, 그 사이에는 WFI로 대기합니다.

**의도적으로 넣지 않은 것 (코드 헤더 주석에 이유를 명시)**:
- Lab 02의 `WDT_FLAG_RESET_SOC`는 여기서 arm하지 않습니다 — 물리 개입 없이는 복구되지 않는 정지 상태를 유발한다는 것이 확인된 이상, "설계 가이드"에 이걸 넣는 건 권장 패턴이 아니라 함정을 보여주는 것이기 때문입니다.
- Lab 04의 `SW7`/`PMU_EN` 경로도 재현하지 않습니다 — 이 SDK 버전에는 그 경로가 깨어나야 할 HW 저전력 모드로 진입시키는 API 자체가 없기 때문입니다.

## 이 SDK/보드의 최종 설계 함의

- **컨텍스트를 보존한 채 깊이 자는 중간 단계가 없습니다.** Zephyr가 정의하는 7단계 System Power State(1-1절) 중 이 SDK가 구현한 것은 사실상 `PM_STATE_RUNTIME_IDLE`(WFI)뿐이고, 그 다음 단계로 넘어가면 바로 `PM_STATE_SOFT_OFF`급의 완전 재부팅(watchdog 리셋)으로 건너뜁니다. `PM_STATE_STANDBY`/`SUSPEND_TO_RAM`처럼 "일부만 켜두고 컨텍스트는 보존"하는 중간 지대는 이 SDK 버전에 없습니다.
- **M4→M55 wake의 공식적이고 확실하게 동작하는 방법은 mbox(Lab 03)뿐입니다.** `RESET_LOW_POWER_WAKE`/`PMU_EN` 경로(Lab 04)는 하드웨어 레벨 존재는 확인되나 소프트웨어로 구동할 방법이 없습니다.
- **watchdog 기반 리셋(Lab 02)은 안전장치로 신뢰하기 어렵습니다.** 트리거되면 정지 상태가 되고, 자동 복구를 보장하지 못합니다. 실제 제품에서 안전장치가 필요하다면, 이 SDK 버전만으로는 부족하고 외부 감시 회로(external watchdog IC 등)를 검토해야 할 수 있습니다.
- 이 세 가지가 이 커리큘럼(Lab 00~05)이 SR110 + Zephyr(`syna_zephyr_sdk-1.0.0`) 조합에 대해 실기로 확인한 전원/wake 관리의 현재 한계이자 설계 가이드입니다.

## 커리큘럼 마무리

Lab 00에서 던졌던 세 가지 질문 — "GPIO 인터럽트로 깨울 수 있는가?", "mbox가 유일한 경로인가?", "M55 자체 wake 트리거는 무엇인가?" — 에 대한 최종 답은: GPIO 인터럽트 경로는 소프트웨어 레벨에서 확인되지 않았고, **mbox가 이 SDK에서 실기로 검증된 유일한 M4→M55 wake 경로**이며, M55 자체 wake 트리거(버튼/RTC/PIR/watchdog) 중 실기로 신뢰할 수 있게 동작하는 것은 없었습니다(watchdog은 불완전, PMU_EN 계열은 SoC가 켜진 상태에서 무반응). 이 커리큘럼은 낙관적인 결론이 아니라, **이 SDK 버전에서 실제로 되는 것과 안 되는 것을 정직하게 실기로 가른** 결과로 마무리됩니다.

**아쉬운 점 (솔직한 회고)**: 이 커리큘럼을 시작할 때의 목표는 SR110이 하드웨어적으로 지원하는 것으로 보이는 Active / Low-power / Ultra-low-power mode 전환을 실습으로 직접 다뤄보는 것이었습니다. 하지만 Lab 00~04로 확인했듯, 이 SDK 버전(`syna_zephyr_sdk-1.0.0`)에는 그 모드들로 진입시키는 소프트웨어 API 자체가 없습니다(`CONFIG_PM` 부재). 그래서 결과적으로 이번에 실습으로 다룰 수 있었던 것은 Zephyr/소프트웨어 레벨의 **Idle → Sleep(WFI) → 다시 Active로 전환하는 정도**(Lab 01)와, 리셋을 동반하는 두 가지 경로(watchdog 리셋 - Lab 02, PMU_EN 계열 - Lab 04)뿐이었습니다. 특히 안전장치로 기대했던 **watchdog 기반 power reset조차 자체 완결되는 형태로는 동작하지 않는다는 것**이 확인되어(Lab 02), 이번 커리큘럼만으로는 "진짜 저전력 모드 전환"이라는 원래 목표에는 이르지 못했습니다. 이 하드웨어 레벨 저전력 모드를 실제로 여는 방법은 Synaptics SDK의 향후 버전이나 별도 문의를 통해서만 확인 가능할 것으로 보이며, 이 커리큘럼은 그 경계선까지 실기로 확인한 결과로 남깁니다.
